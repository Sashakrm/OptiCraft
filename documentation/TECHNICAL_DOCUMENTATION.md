# OptiCraft --- Technical Documentation

**Документ описывает состояние исходного кода**\
Версия C++: C++20. Основная реализация находится в `src/`; сборка
выполняется через CMake.

------------------------------------------------------------------------

## 1. Назначение и границы проекта

OptiCraft --- воксельный 3D-движок/игровой прототип на C++ с:

-   32×32×32 воксельными чанками;
-   процедурной генерацией мира на OpenSimplex2S;
-   климатическими полями и 23 биомами;
-   3D-пещерами и подземными биомами;
-   плавающими небесными островами;
-   детерминированной генерацией деревьев и декораций;
-   потоковой загрузкой/выгрузкой чанков;
-   сохранением изменённых чанков;
-   асинхронной генерацией и пересборкой мешей;
-   мешем, разбитым на Y-секции;
-   frustum culling, отсечение укрытий по связности секций и GPU occlusion culling (выключен по умолчанию);
-   отдельными проходами для обычных блоков, флоры и жидкости;
-   блоковым освещением;
-   физикой игрока, raycast и редактированием блоков;
-   Creative/Survival режимами;
-   циклом дня/ночи;
-   HUD, инвентарём и экранными состояниями.

Документ фиксирует **реальное поведение текущего кода**, а не
исторический план разработки.

## 2. Сборка

### Требования

`CMakeLists.txt` задаёт:

-   CMake ≥ 3.16;
-   C++20 без compiler extensions;
-   OpenGL;
-   GLFW3;
-   X11 и Threads на UNIX, кроме Apple;
-   GLAD включён в репозиторий;
-   stb включён в репозиторий.

По умолчанию, если тип сборки не указан, CMake выбирает `Release`.

Опция:

``` text
-DOPTICRAFT_NATIVE_ARCH=ON
```

добавляет `-march=native` на поддерживаемых non-MSVC сборках. Это
ускоряет вычисления, но снижает переносимость бинарника на старые CPU.

### Сборка

``` bash
cmake -S . -B cmake-build-debug
cmake --build cmake-build-debug -j 4
```

После сборки каталог `assets/` автоматически копируется рядом с
исполняемым файлом.

## 5. Координаты чанка

Для мировых координат используется floor division:

``` text
chunk_x = floor(world_x / 32)
chunk_y = floor(world_y / 32)
chunk_z = floor(world_z / 32)

local_x = world_x - chunk_x * 32
local_y = world_y - chunk_y * 32
local_z = world_z - chunk_z * 32
```

Это особенно важно для отрицательных координат: обычное целочисленное
усечение C++ здесь не используется.

`Chunk_Manager::get_block_world()`:

1.  проверяет мировой Y;
2.  переводит мировую позицию в chunk/local coordinates;
3.  если чанк загружен --- читает его реальные данные;
4.  если чанк не загружен --- использует `World_Generator::get_block()`
    как процедурный fallback;
5.  вне мирового Y возвращает `Air`.

Для block light fallback отсутствует: если чанк не загружен,
`get_light_world()` возвращает 0.

## 6. Хранение данных чанка

### Block IDs

`Chunk_Block_Grid` содержит:

``` text
32 × 32 × 32 = 32768 voxels
32768 × uint8_t = 32768 bytes = 32 KiB
```

Индекс:

``` text
((y * 32) + z) * 32 + x
```

Реестр допускает до 65536 ID (`Block_ID` — uint16). Палитра чанка хранит
полноценные ID; ширина записи палитры растёт 1 → 2 → 4 → 8 → 16 бит (см. Chunk.h).

### Block light

`Chunk_Light_Grid` хранит два значения света в одном байте:

``` text
4 bits + 4 bits
```

При 32768 клетках:

``` text
16384 bytes = 16 KiB
```

Диапазон света: `0..14`.

### Горячие данные

Итого два основных воксельных массива:

``` text
32 KiB blocks + 16 KiB light = 48 KiB / chunk
```

Данные непрерывны и не используют отдельные heap-объекты на каждый
voxel.

## 7. Реестр блоков

`Block_Types` содержит именованные ID для блоков, которые нужны C++
напрямую. Однако реестр не ограничен `Block_Types::Count`.

`Block_Registry` имеет потолок пространства ID и растущую ёмкость:

``` text
k_max_block_types = 65536          // потолок id (Block_ID = uint16)
Block_Registry::id_capacity()      // max зарегистрированный id + 1 (растёт при загрузке)
```

Таблицы свойств растут по `id_capacity()`; плоские кэши (прозрачность, свет, взрыв)
и флаги мешера фиксированы на потолке 65536 (около 1 МБ). GPU-LUT — по `id_capacity()`.

Блоки могут регистрироваться data-driven через:

``` text
assets/blocks.json
```

Свойства блока:

-   имя;
-   `solid`;
-   `transparent`;
-   `opaque`;
-   `can_update`;
-   `hardness`;
-   `mesh_type`;
-   `mesh_style`;
-   `state`;
-   texture index для top/side/bottom;
-   `light_emission`.

Поддерживаемые mesh types:

-   `Solid`;
-   `Flora`;
-   `Liquid`.

Mesh styles:

-   `Block`;
-   `XStyle`.

Состояния:

-   `Solid`;
-   `Liquid`;
-   `Gas`.

ID 8 зарезервирован согласно `reserved_block_ids` в `blocks.json`.

Именованные ID контейнеров: `Chest = 50`, `Crafting_Table = 51`,
`Furnace = 52` (`Block_Types::Count = 53`). Тайлы атласа у них пока
временные --- повторно использованы уже занятые тайлы других блоков,
свободных в `blocks_main` нет.

## 8. Основной генератор мира

`World_Generator` использует OpenSimplex2S.

Один seed преобразуется в независимые seed'ы для полей:

1.  temperature;
2.  humidity;
3.  continentalness;
4.  erosion;
5.  weirdness;
6.  terrain;
7.  detail;
8.  mountain;
9.  caves.

Для этого применяется детерминированный `derive_seed()` на основе
`splitmix64`.

Одинаковые:

``` text
seed + world coordinates + generation folder
```

дают одинаковый процедурный результат.

------------------------------------------------------------------------

## 9. Поля климата и рельефа

Для каждой X/Z-колонки вычисляются:

-   temperature;
-   humidity;
-   continentalness;
-   erosion;
-   weirdness;
-   mountainness;
-   depth parameter;
-   surface height;
-   slope;
-   near-ocean.

Колонка кэшируется в thread-local direct-mapped cache.

Размеры текущих кэшей:

-   terrain cache: 8192 terrain points;
-   column cache: 4096 columns;
-   cave-cell cache: 2048 cells.

Кэш содержит epoch генератора, поэтому после создания нового генератора
старые thread-local записи автоматически становятся недействительными.

### Высота поверхности

Уровень моря:

``` text
Y = 63
```

Базовая высота строится непрерывным сплайном по continentalness с
узлами:

``` text
C=-1.00 -> Y=17
C=-0.62 -> Y=33
C=-0.34 -> Y=50
C=-0.17 -> Y=59.5
C=-0.06 -> Y=65
C= 0.10 -> Y=71
C= 0.38 -> Y=81
C= 0.70 -> Y=93
C= 1.00 -> Y=107
```

Между узлами используется smoothstep.

Дополнительный рельеф состоит из:

-   broad terrain FBM;
-   detail terrain FBM;
-   mountain signal.

Горный член масштабируется через land/erosion/shore masks. Поэтому горы
не обрываются вертикальным условием на береговой границе.

Итоговая высота ограничивается:

``` text
world_min_y + 1 .. world_max_y
```

то есть `-255..1024`.

## 10. Вода и берег

Вода не вырезает terrain.

Алгоритм колонки:

``` text
if world_y > surface_height:
    if world_y <= 63 -> Water
    else             -> Air
```

Следовательно, вода заполняет всё пространство между поверхностью и
уровнем моря независимо от continentalness.

Тип дна зависит от глубины:

-   до 5 блоков ниже моря --- Sand;
-   далее до 14 --- Sand/Gravel;
-   далее до 30 --- Gravel/Stone;
-   глубже --- преимущественно Stone с Gravel.

Пляж выбирается по высоте, температуре и slope:

-   поверхность около уровня моря;
-   не более примерно 3 блоков выше моря;
-   slope \< 2.6;
-   температура \> 0.18.

Это предотвращает появление пляжного материала на крутых склонах.

## 11. Биомы

Основной `World_Generator` регистрирует 23 биома:

1.  Ocean
2.  Shallow Water
3.  Beach
4.  Plains
5.  Forest
6.  Birch Forest
7.  Taiga
8.  Jungle
9.  Savanna
10. Desert
11. Stone Desert
12. Steppe
13. Tundra
14. Ice Fields
15. Mountains
16. High Mountains
17. Plateau
18. Slime
19. Solar
20. Sky
21. Underground
22. Deep Underground
23. Flooded Underground

Обычные наземные биомы выбираются по расстоянию климатической колонки до
диапазонов шести параметров:

``` text
temperature
humidity
continentalness
erosion
weirdness
depth
```

Выбирается минимальная квадратичная дистанция. При полном равенстве
используется priority.

Mountains, High Mountains и Plateau дополнительно требуют mountainness:

``` text
Mountains      > 0.55
High Mountains > 0.70
Plateau        > 0.50
```

Ocean/Shallow Water/Beach определяются отдельной логикой по фактической
высоте поверхности.

Slime --- редкое условное прибрежное исключение.

## 12. Вертикальные/подземные биомы

`biome_at()` дополнительно проверяет Y и пещерные сигналы.

### Sky

При:

``` text
Y > 200
humidity > 0.70
continentalness < 0.60
```

возвращается `Sky`.

### Solar

При:

``` text
Y > 80
mountainness > 0.75
erosion > 0.75
```

возвращается `Solar`.

### Underground

Пещерная зона начинается только при:

``` text
Y < -10
cave_density > 0.58
```

Далее:

-   `Deep Underground` --- ниже -150, density \> 0.75, нет surface
    connection, temperature \> 0.70;
-   `Flooded Underground` --- от -150 до -15, density \> 0.60, water
    connection, humidity \> 0.85;
-   иначе `Underground`.

## 13. Пещеры

Порог пещер:

``` text
kCaveThreshold = 0.58
```

### Тоннели

Используются два независимых 3D FBM-поля с:

``` text
frequency = 0.018
octaves   = 3
lacunarity = 2.0
gain       = 0.5
```

Оба поля должны находиться близко к нулю:

``` text
abs(noise) < 0.16
```

Их пересечение образует протяжённые тоннели.

### Каверны

Низкочастотное 3D-поле:

``` text
frequency = 0.0055
octaves   = 3
lacunarity = 2.0
gain       = 0.55
```

Залы начинают влиять глубже примерно 80 блоков под поверхностью. Для
сильных значений:

``` text
chambers > 0.85
```

сигнал масштабируется глубиной.

### Защита поверхности

Первые 4 блока под поверхностью не вырезаются.

Для подводной поверхности крыша увеличена до 10 блоков. Это
предотвращает массовое вскрытие океана пещерами.

### Связность

Связность считается не на каждом voxel, а на сетке 16×16×16.

BFS:

-   шаг: 2 блока;
-   максимум: 320 nodes;
-   горизонтальный радиус: 96;
-   вертикальный радиус: 128.

Отдельно определяются:

-   `surface_connected`;
-   `water_connected`.

Эти флаги используются подземными биомами и Flooded Underground.

## 14. Небесные острова

Sky islands проверяются только при:

``` text
Y >= 200
```

Пространство разбито на клетки X/Z размером 384.

Для ближайшего кандидата детерминированно выбираются:

-   центр;
-   anchor validity;
-   основной радиус;
-   высота.

Anchor считается допустимым, если исходная поверхность в этой точке либо
горная, либо океаническая.

Основной остров:

-   горизонтальный радиус примерно 80..175;
-   кластер может проверяться в радиусе до 375;
-   верхняя поверхность имеет небольшую куполообразность;
-   низ расширяется вниз, образуя подвешенное основание;
-   форма дополнительно деформируется detail noise.

Кроме главного острова генерируется до 18 малых спутниковых формаций.

Материал:

-   открытая верхняя поверхность --- Grass;
-   остальной остров --- Cloud Stone.

Параметры зависят от seed и координат, поэтому границы чанков не создают
отдельные острова или швы.

## 15. Пакетная и параллельная генерация чанков

`World_Generator::generate_chunk()` не вызывает полный `get_block()`
32768 раз. Для каждой из 1024 X/Z-колонок вычисляется общий `Column`, после
чего выполняется voxel-проход в порядке непрерывной памяти (Y, Z, X).

В потоковом менеджере поколение разбито на два этапа:

1. `Chunk_Column_Job` объединяет отсутствующие сохранённые чанки одной X/Z-колонки.
   Существующие на диске чанки читаются отдельно и не перегенерируются.
2. `World_Generator::prepare_chunk_column()` один раз рассчитывает общие поля
   рельефа/климата/реки/деревни и профиль пещер для запрошенных уровней Y.
   Подготовленный контекст далее неизменяемый.
3. `Chunk_Build_Job` для каждого уровня передаётся обратно в общий пул worker-потоков.
   `generate_prepared_chunk()` заполняет и упаковывает свой чанк независимо от соседних
   уровней; worker сразу завершает декорации и метаданные для этого чанка.
4. Очередь мешей сохраняет приоритет над генерацией, чтобы большая очередь террейна
   не блокировала интерактивные правки блоков.

Все шесть доступных worker-потоков могут обрабатывать как меши, так и генерацию; отдельный
поток чтения диска остаётся. Количество worker'ов по-прежнему ограничивается доступными
логическими CPU и верхним пределом 6.

Кэш пещер/рек строится лениво по регионам. Первый запрос нового региона может занимать
существенно больше времени, чем последующие чанки, поскольку регион содержит общую
геометрию пещер/воды. Это разовая стоимость регионального кэша, а не постоянная стоимость
каждого чанка; при замерах производительности отдельно учитывайте холодный и прогретый кэш.

Headless-замер пакета из 9 уровней на seed 1327 (6 тестовых worker-потоков, `-O3`):
после прогрева региональных кэшей измерено примерно 22–25 мс на полный пакет. Первый
холодный пакет занял около 730 мс из-за ленивого построения кэшей пещер/рек и прогрева
локальных кэшей генератора. Это замер конкретного тестового окружения, не гарантия для
любого процессора; холодный проход пока не укладывается в цель 27 мс и должен оцениваться
отдельно от устойчивой скорости потока чанков.

Если чанк заведомо не может содержать блоков, он заполняется воздухом без шумов. Sky-island
путь активируется только для чанков, пересекающих Y=200. Эти быстрые пути не меняют формулы
шумов, правила биомов, пещер, рек или декораций.

------------------------------------------------------------------------

## 16. Декорации и деревья

`decorate_column()` работает только там, где поверхность находится в
текущем вертикальном чанке с запасом на высоту структуры.

Декорации не размещаются:

-   ниже уровня моря;
-   на Snow Block;
-   на Ice;
-   на Slime Block;
-   на Sand;
-   на Gravel.

Также используется проверка фактической поверхности.

### Флора

-   Jungle → Fern;
-   Forest/Birch Forest → Tall Grass;
-   Taiga/Tundra → Fern;
-   Plains/Steppe/Savanna → Tall Grass или Flower;
-   Slime → Slime Grass.

Перед записью flora проверяется, что целевой voxel является Air.

### Деревья

Поддерживаются:

-   Oak;
-   Palm;
-   Acacia;
-   Birch;
-   Spruce;
-   Jungle;
-   Slimewood.

Тип и частота зависят от биома.

Дерево не ставится при slope \> 4.

Ключевая гарантия: setter дерева записывает блок только если
`get_block(x,y,z) == Air`. Поэтому структура не должна перезаписывать
воду или рельеф.

Генератор дерева принимает абсолютные мировые координаты. Если часть
структуры выходит за границу текущего чанка, setter просто записывает
только ту часть, которая принадлежит текущему чанку. Следовательно,
структура рассчитывается единообразно по мировым координатам, а не по
локальным координатам чанка.

------------------------------------------------------------------------

## 17. Chunk Manager и потоковая загрузка

`Chunk_Manager` --- центральный владелец загруженных чанков.

Он содержит:

``` text
unordered_map<chunk_position, unique_ptr<Chunk>>
```

и множества:

-   requested chunks;
-   pending mesh rebuilds;
-   mesh requeue.

### Потоки

Количество worker'ов:

``` text
max(2, hardware_concurrency - 2)
```

при условии, что hardware concurrency \> 2; иначе минимум 2 worker'а.

Последний worker является dedicated mesh worker.

### Очереди

Есть две приоритетные очереди:

1.  генерация/загрузка чанков;
2.  пересборка мешей.

Меньшее значение `priority` означает более срочную работу.

Mesh jobs имеют абсолютный приоритет над generation jobs.

Dedicated mesh worker вообще ждёт только mesh queue.

------------------------------------------------------------------------

## 18. Приоритет загрузки

Приоритет чанка:

``` text
dx² + dz² + 4 * dy²
```

где:

``` text
dx = chunk_x - player_chunk_x
dz = chunk_z - player_chunk_z
dy = chunk_y - player_chunk_y
```

Вертикальное расстояние умножается на 4, поэтому горизонтально близкий
текущий этаж обслуживается раньше далёких вертикальных слоёв.

Важно: приоритет вычисляется в момент постановки задачи и потом не
пересчитывается, пока задача находится в очереди.

------------------------------------------------------------------------

## 19. Вертикальный streaming

По X/Z загружается квадрат:

``` text
[player_chunk - radius, player_chunk + radius]
```

По Y загружается окно:

``` text
player_chunk_y ± 8
```

с ограничением мировыми chunk-Y `[-8, 32]`.

Это означает:

-   полный мировой диапазон остаётся процедурно доступным;
-   одновременно не требуется держать все 41 вертикальных чанка;
-   при полёте вверх/вниз вертикальное окно сдвигается;
-   удалённые по X/Z или Y чанки выгружаются.

------------------------------------------------------------------------

## 20. Жизненный цикл загрузки чанка

Worker получает `Chunk_Job`.

Далее:

1.  создаётся `Chunk`;
2.  проверяется постоянное хранилище;
3.  если чанк найден и валиден --- блоки загружаются;
4.  иначе выполняется процедурная генерация;
5.  строится первичный mesh;
6.  результат помещается в completed queue;
7.  главный поток вставляет чанк в `m_chunks`;
8.  сам чанк и шесть соседей помечаются dirty;
9.  после появления соседа выполняется корректная пересборка границ.

Это важно для устранения артефактов на границах чанков.

`generation_id` защищает от применения результата старого мира после
переключения генератора/мира.

------------------------------------------------------------------------

## 21. Асинхронная пересборка меша

При изменении блока или появлении соседа создаётся `Mesh_Job`.

В worker передаются не указатели на живые чанки, а снимки:

-   собственный `Chunk_Block_Grid` --- 32 KiB;
-   собственный light grid --- 16 KiB;
-   до шести однослойных block faces;
-   до шести однослойных light faces;
-   кольцо из 392 клеток рёбер и углов (`Chunk_Ring`) с признаком наличия
    соседа --- для AO, которое читает диагональных соседей.

Один face содержит 32×32 значений, поэтому копирование соседей намного
дешевле копирования шести полных чанков.

Если пересборка уже выполняется и чанк изменился снова:

-   в `m_mesh_rebuild_requeue` ставится флаг;
-   после завершения текущего job ставится новая задача со свежим
    snapshot.

Снимок запоминает два значения: `dirty_epoch` --- счётчик пометок
грязности (`Chunk::mark_mesh_dirty()` его увеличивает) и `instance_id` ---
уникальный номер объекта `Chunk`, который выдаётся в конструкторе из
глобального счётчика. Результат применяется только к тому же объекту:

-   если объект на позиции выгружен или заменён (выгрузили и загрузили
    заново), результат тихо отбрасывается. Состояние позиции
    (`m_pending_mesh_rebuilds`, `m_mesh_rebuild_requeue`) при этом не
    трогается: оно уже принадлежит новой задаче;
-   если объект тот же, но `dirty_epoch` вырос, правка легла после снимка:
    `apply_mesh()` выполняется, и сразу ставится ещё одна задача.

Сравнения одной позиции недостаточно: счётчик эпохи у каждого объекта свой,
поэтому старый и новый чанки на одной позиции могут совпасть по значению.

Старый mesh остаётся видимым до готовности нового.

Это позволяет не блокировать главный поток на `build_mesh()`.

------------------------------------------------------------------------

## 22. Потокобезопасность

`Chunk_Manager` **не является полностью thread-safe**.

Основные методы управления миром должны вызываться из одного
главного/игрового потока:

-   `get_chunk`;
-   `set_block_world`;
-   `load_around`;
-   `update_player_position`;
-   `collect_finished_*`;
-   `rebuild_dirty_chunks`;
-   и т.д.

Worker'ы работают с защищёнными очередями задач/результатов и с
независимыми snapshot-данными.

------------------------------------------------------------------------

## 23. Mesh building

Мешинг целиком выполняется на GPU (OpenGL 4.3, compute-шейдеры). CPU-мешера и
CPU-отката больше нет; контекст ниже 4.3 не поддерживается (`Window.cpp`).

CPU в рабочем потоке (`build_chunk_gpu_mesh()`) делает только три вещи:

-   упаковывает блоки, meta и свет чанка и его соседей в палитровые каналы
    полезной нагрузки (блоки, meta, свет, грани соседей, кольцо диагоналей);
-   считает связность Y-секций (флуд-заливка, см. ниже) и маски видов
    геометрии (solid / shaped / flora / liquid) для отсечения по окклюзии;
-   отдаёт нагрузку в главный поток, где она загружается в SSBO.

Compute-шейдеры:

-   `mesh_greedy.comp` — жадное слияние граней полных кубов (solid);
-   `mesh_misc.comp` — формы (ступени, плиты, «plate», кнопка, провод), флора и жидкость:
    по одной записи на грань, без слияния;
-   `mesh_finalize.comp` — собирает команды `DrawArraysIndirect` по секциям для
    каждого вида.

### Пул квадов

Единый пул записей квадов с блочным CPU-аллокатором (блок = 32 квада). У чанка
один handle и 16 потоков (вид × 4 секции). Счётчики и диапазоны лежат в SSBO по
индексу `handle*16 + kind*4 + section`. Если секции не хватило места, шейдер
считает точное число квадов, оно асинхронно читается обратно, CPU расширяет
выделение и ставит чанк на перемешивание. Откат на CPU не используется. Слишком
большие выделения со временем сжимаются.

Запись misc-квада: `x` = клетка (5/5/5 бит) | грань (3) << 15 | свет (8) << 18;
`y` — индекс прямоугольника атласа; для форм `z/w` — бокс в 1/64 блока, для
жидкости `z/w` — высоты четырёх углов (по 16 бит).

### Формы Button и Wire

`Block_Shape::Button` — кнопка 3×2×2 пикселя на грани опоры: `meta & 7` — индекс стороны опоры
(+X, −X, +Y, −Y, +Z, −Z, как в `Logic_Manager`). `Block_Shape::Wire` — провод 12×2×12 пикселей по центру
клетки у пола. Боксы берёт `shape_boxes()`, поэтому мешер, коллизия и прицел совпадают. Для этих форм луч
(`Raycast::cast`) проверяет сами боксы (`shape_has_precise_hitbox`), а подсветка (`Hud::draw_box_highlight`)
обводит попавший бокс, а не всю клетку.

### Порядок мешинга и выгрузка

Меши новых чанков строятся строго от центра к краю (`first_incomplete_ring`): чанк кольца r ждёт, пока
загружены все нужные чанки колец до r+1. Правка блока ставит срочную пересборку (`request_urgent_mesh_rebuild`):
она идёт первой, возвращается по отдельной очереди результатов, а результат устаревшей задачи отбрасывается по
`seq`. Выгрузка при смене высоты плавная: по Y держится запас в один слой, лишнее убирается порциями
(`unload_distant`).

### Y sections

32 блока по Y разбиваются на 4 секции по 8 слоёв (0..7, 8..15, 16..23, 24..31).
Каждая секция хранит диапазоны квадов для каждого вида геометрии.

### Связность секций

Для каждой Y-секции (32×8×32) `build_chunk_gpu_mesh()` считает связность
(`compute_section_connectivity()`, результат — `Chunk_Section_Range::conn`):

-   проходимые клетки — всё, что не `Mesh_Tables::occludes` (воздух, вода,
    стекло, листва, флора);
-   компоненты проходимых клеток внутри секции (заливка по клеткам);
-   граничные позиции секции (3072) относятся к компонентам; для каждой грани
    хранится битовая маска позиций каждой компоненты;
-   вид связности: `Open` — граница полностью проходима и образует одну
    компоненту (или компонент больше 255: консервативный откат); `Closed` —
    ни одна граничная клетка не проходима; `Mixed` — маски по граням.

Секция из одного воздуха не считается: её связность по умолчанию `Open`.

Эпоха связности (`current_connectivity_epoch()`) растёт только тогда, когда
связность чанка реально изменилась: `build_mesh()` и `apply_mesh()` сравнивают
старый и новый результат. Правка блока, которая не меняет проходимость,
кэш обхода не сбрасывает.

## 24. Рендеринг

`Renderer` использует отдельные GPU resources на чанк:

-   solid VAO/VBO;
-   flora VAO/VBO;
-   liquid VAO/VBO.

Версия mesh (`mesh_version`) позволяет переотправлять GPU данные только
после изменения CPU mesh.

### Frustum culling

Сначала `Chunk_Manager::get_renderable_chunks()` проверяет AABB каждой
Y-секции чанка и передаёт renderer только чанки с видимыми секциями.
Для каждой секции сохраняется флаг `section_visible` (секция во фрустуме и достижима от камеры, см. ниже), поэтому renderer
не повторяет эти проверки. Дальность флоры также применяется на этом этапе.

### Отсечение укрытий (достижимость от камеры)

Frustum culling не отсекает секции пещер, закрытые камнем, если они попали в
конус обзора. Поэтому поверх фрустума работает обход по связности
(`build_section_reach()`, `compute_section_reach()`):

-   узлы обхода — пары (секция, компонента проходимых клеток); старт —
    все компоненты секции камеры;
-   из `Open`-секции проход идёт во все шесть соседей; из `Mixed` — только
    через компоненты, у которых есть позиции на общей грани (пересечение
    масок). Полости, закрытые камнем, так не склеиваются с воздухом камеры;
-   секция рисуется, если в неё вошли или к ней примыкает достижимый воздух:
    её грань, обращённая к воздуху, видна, даже если сама секция непроходима;
-   обход идёт по сетке чанков загруженной области с рамкой в один чанк.
    Незагруженный чанк внутри области считается открытым, рамка — закрытой.
    Камера внутри выпуклой загруженной области видит только клетки, луч до
    которых лежит внутри неё, поэтому ограничение областью точное;
-   монотонное правило: прямой луч из глаза по каждой оси движется в одну
    сторону. Поэтому выход из секции через грань разрешён, если по этой оси
    секция либо на одной плоскости с камерой, либо уже дальше от неё в сторону
    этой грани. Смещение считается от секции камеры, дополнительного состояния
    не нужно. Без правила обход шёл в обе стороны и протекал через пещеры
    (радиус 2: 415 секций на камеру вместо 67);
-   отсечение не применяется (рисуется всё, как раньше), если секция камеры
    закрыта, камера вне области, сетка больше 65 536 чанков с рамкой или глаз
    стоит в непроходимой клетке (камень, `/tp` в стену): обзора из воздуха там
    нет, а кадр иначе менялся бы;
-   ограничение: точный проход луча ровно через ребро между двумя проходимыми
    клетками без общей грани обход не учитывает (переходы по рёбрам и углам не
    реализованы). В замере один пиксель кадра показывал фон вместо камня.
    Учёт рёбер и углов добавляет примерно 8–10% секций (по эталону).

Результат кэшируется в `thread_local` состоянии `Reach_Scratch`. Ключ кэша:
владелец, эпоха набора чанков (`m_chunk_set_epoch`), эпоха связности,
чанк и секция камеры. Пока они не менялись (движение внутри секции, поворот
камеры), обход не выполняется. Смена набора чанков, связности или секции
камеры — пересчёт.

Проверено сверкой с эталонным обходом по клеткам (харнесс вне репозитория): на
48 камерах при радиусе 2 и при радиусе 5 пропущенных нужных секций нет
(`missed = 0`), лишних тоже (`extra = 0`), в том числе после правок блоков и при
повторном вызове той же камеры (попадание в кэш). Лучевая сверка (720×360 лучей
DDA): видимых секций, отсечённых обходом, нет.

Замеры, среднее на камеру (секции с геометрией, без фрустума): радиус 2 — 909
секций → 67 достижимых; радиус 5 — 4367 → 216. Без монотонного правила (только
грани) было бы 415 и 1655. Пересчёт `get_renderable_chunks`: 0,04 мс (радиус 2)
и 0,27 мс (радиус 5), из кэша 0,01–0,04 мс.

### Section culling

Внутри чанка renderer работает с четырьмя Y-секциями, поэтому можно
отбросить отдельную секцию без удаления остальных.

### GPU occlusion culling

Выключен по умолчанию (`Renderer::m_occlusion_enabled = false`, см. README): отсечение укрытий по связности работает без задержки в кадр.

Для секций используется `GL_ANY_SAMPLES_PASSED`.

Результат query читается без блокировки в следующем кадре. Если
результат ещё не готов, используется предыдущая видимость.

Во время occlusion query `GL_CULL_FACE` отключается, чтобы камера,
находящаяся внутри AABB секции, не получила ложный результат "невидимо".

Для уменьшения z-fighting используется `glPolygonOffset`.

## 25. Проходы рендера

В `Renderer::render_chunks()` используются отдельные категории:

1.  opaque/solid;
2.  flora;
3.  liquid.

Флора может дополнительно ограничиваться отдельной дальностью в чанках.

Текущая настройка:

``` text
default flora distance = 4
maximum = 12
```

Солнце и луна рисуются отдельным процедурным sky pass до геометрии мира.
Они не пишут depth, поэтому непрозрачный terrain естественно перекрывает
их.

------------------------------------------------------------------------

## 26. Прозрачность и жидкости

Флора использует cutout/alpha discard и запись depth.

Жидкость использует alpha blending и сортировку чанков по глубине для
liquid pass.

Liquid shader реализует:

-   анимацию верхней поверхности;
-   движение UV внутри tile атласа;
-   изменение яркости;
-   прозрачность.

Таким образом более дальняя жидкость не должна визуально перекрывать
более близкую только из-за порядка отрисовки.

------------------------------------------------------------------------

## 27. Block light

Block light хранится отдельно от ambient day/night.

Источники определяются через:

``` text
Block_Properties::light_emission > 0
```

Сейчас таким блоком является Sun Stone.

Максимальный уровень:

``` text
14
```

Свет распространяется BFS в шести направлениях.

На каждом шаге уровень уменьшается на 1.

Свет не проходит через блок, для которого:

``` text
is_transparent == false
```

Пересчёт является **полным в ограниченной области**, а не
инкрементальным de-propagation.

`recompute_lighting()` вызывается из `set_block_world()` при **каждой**
правке блока (раньше --- только если блок стал/перестал быть источником
или правка попала в радиус существующего источника). Список
`m_light_sources` при этом обновляется только когда старый/новый блок
реально излучает свет; пересчёт всегда идёт по актуальному списку, поэтому
новый источник загорается сразу.

Очищается область вокруг текущих источников и дополнительно вокруг
только что удалённого источника. Затем BFS заново распространяет свет от
всех оставшихся источников.

После изменения света затронутые чанки помечаются dirty и их mesh
пересобирается асинхронно. Кроме того, шесть соседей по граням тех
чанков помечаются dirty (`mark_light_neighbors_dirty`): граничные грани
соседа читают свет через границу, и без этого стык держал бы старое
значение. Пометка соседей выполняется и для пересчёта света без изменений
(консервативно, без сравнения значений).

Свет не связан с ambient интенсивностью дня/ночи.

## 28. Сохранение мира

Основной файл настроек:

``` text
worlds/default/world.json
```

Содержит:

``` json
{
  "name": "Default World",
  "generation_folder": "Classic",
  "seed": 1327
}
```

`World_File` читает эти три поля.

### Region storage

Чанки одного generation folder находятся в:

``` text
worlds/default/chunks/Classic.region
worlds/default/chunks/Islands.region
```

Поэтому Classic и Islands физически разделены.

### Region format

Файл использует:

-   magic `OPCR`;
-   version 1;
-   sector size 512 bytes;
-   64-byte header;
-   индекс записей по 32 bytes.

Запись чанка содержит:

``` text
x, y, z
first_sector
sector_count
payload_bytes
format
```

Поддерживаются:

``` text
format 0 = raw
format 1 = RLE
```

RLE хранит пары:

``` text
uint8 value
uint16 run length
```

Если RLE получается длиннее исходных данных, сохраняется raw payload.

### Надёжность индекса

Новый индекс пишется в конец файла.

Только после успешной записи/flush обновляется `index_offset` в
заголовке.

При падении процесса заголовок поэтому продолжает ссылаться на
предыдущий валидный индекс.

------------------------------------------------------------------------

### Block entities

Содержимое контейнеров в Region_File **не** хранится: его формат рассчитан
ровно на блоки чанка. Вместо этого рядом с `world.json` пишется отдельный
файл на пресет генерации:

``` text
worlds/<world>/block_entities_<generation_folder>.json
```

Формат:

``` json
{"entities":[
  {"x":1,"y":2,"z":3,"type":"chest","paired_dx":1,"paired_dz":0,
   "slots":[{"slot":3,"item":"Stone","count":7}]}
]}
```

Пустые слоты не пишутся. Предмет хранится по имени блока (не по ID), поэтому
переупорядочивание ID в `blocks.json` файл не ломает; неизвестные имена и
слоты вне диапазона при загрузке молча пропускаются.

Загрузка --- в `Chunk_Manager::set_world_storage()`; сохранение --- в
`save_all()` (вызывается и из деструктора) и при смене пресета генерации.
Файл читается/пишется целиком, карта `world_pos -> Block_Entity`
живёт в `Chunk_Manager::m_block_entities`.

------------------------------------------------------------------------

## 29. Правило сохранения изменённых чанков

Каждый `Chunk` имеет `m_is_modified`.

Нетронутый процедурный чанк не записывается на диск, потому что его
можно полностью восстановить из seed.

Изменённый чанк сохраняется:

-   при выгрузке;
-   при `Chunk_Manager::save_all()`;
-   при уничтожении `Chunk_Manager` на выходе.

При обычном изменении блока чанк помечается modified, но запись на диск
не выполняется синхронно в середине кадра.

Это убирает дорогостоящую запись 32 KiB на каждую правку.

------------------------------------------------------------------------

## 30. Совместимость старых chunk saves

`World_File` всё ещё умеет читать старые отдельные файлы:

``` text
worlds/default/chunks/<generation>/c_x_y_z.bin
```

под старым magic `OPC1`, versions 1/2.

При отсутствии записи в `.region`:

1.  проверяется старый `c_x_y_z.bin`;
2.  файл читается;
3.  содержимое переносится в region file;
4.  исходный legacy-файл удаляется после успешной записи.

Новые сохранения в старом формате не создаются.

Это compatibility path внутри кода хранения и не требует отдельного
документа миграции.

## 31. Редактирование блоков

`Block_Interaction` каждый кадр делает raycast из позиции глаз по
направлению камеры.

Максимальная дальность берётся из константы `k_max_reach` в
`Block_Interaction.cpp`.

### ЛКМ

Если raycast попал в блок:

``` text
set_block_world(..., Air)
```

В Survival сломанный блок добавляется в инвентарь.

### ПКМ

Если блок, на который смотрит игрок, является контейнером (у типа блока
есть `Block_Entity_Type`), блок не ставится: `Block_Interaction` сохраняет
запрос на открытие (`has_container_open_request()`), а `Game::
update_gameplay()` забирает его и открывает `Container_Session`.

Иначе целевая позиция берётся из `place_x/y/z`.

Установка запрещается, если:

-   позиция слишком близко к глазам;
-   новый блок пересекается с AABB игрока;
-   в Survival нет нужного ресурса.

После изменения пересобираются:

-   текущий чанк;
-   соседние чанки по границе, если блок стоял на грани.

## 33. Инвентарь и режимы

Есть:

-   хотбар на 9 слотов;
-   полноэкранная сетка по E;
-   страницы Creative inventory;
-   режимы Creative и Survival.

В Creative сетка показывает зарегистрированные блоки.

В Survival предметы представляют реальные собранные ресурсы.

Выбор блока в хотбаре выполняется клавишами `1..9`.

Инвентарь и контейнеры (сундук/верстак/печь) рисует одна универсальная панель
`Hud::draw_panel_screen`. Геометрия панелей --- чистые функции в
`src/hud/layouts/Panel_Layouts.*` (`inventory_survival`, `inventory_creative`, `chest`,
`crafting_table`, `furnace`): они возвращают `Hud_Panel_Layout` со слотами,
подписями и индикаторами прогресса в GUI-пикселях. Каждый слот несёт `id`
(см. `Panel_Layouts::Panel_Slot_Ids`), а `Game::build_inventory_panel` /
`build_container_panel` по этим `id` заполняют содержимое слотов. Чтобы добавить
новый контейнер, нужна новая функция раскладки и ветка сопоставления `id` в `Game`.

### Иконки блоков

Обычные блоки (`mesh_style: Block`, не предметы) рисуются в слотах изометрическим кубом с тремя
гранями: верх, левая и правая (`Hud::draw_slot_icon`). Грани берутся из атласа блоков через
`Block_Properties::textures`; у блоков с лицом (печь, сундук, верстак) лицо стоит на левой грани.
Предметы и «крестики» остаются плоскими (`uv_icon`).

### Голод и лечение

Модель как в Minecraft 1.8 (`Player::update_hunger`, константы в `Config.h`): еда 0..20, насыщение,
истощение. Естественное лечение зависит от сытости: при полной еде и насыщении быстрое
(раз в 0.5 с, лечит `min(насыщение, 6) / 6` HP и столько же тратит истощения), при еде >= 18
обычное (+1 HP раз в 4 с), ниже --- здоровье не восстанавливается. Еду едят удержанием ПКМ
(`Config::eat_duration`) на предмете с полем `food`/`saturation` в `blocks.json`.

### Интерфейс и атлас `ui_main`

Весь интерфейс рисуется пакетно из атласа `ui_main`
(`assets/atlases/ui_main.atlas.json` + `assets/texture/ui_atlas.png`) в «GUI-пикселях»
с целым масштабом (`Hud::get_gui_scale`). **Источник правды --- PNG**; скрипт
`tools/gen_ui_atlas.py` остался как удобный способ добавить спрайты и воспроизводит
текущий PNG побитно. Иконки блоков лежат в другом атласе, поэтому они идут отдельным
пакетом (`begin_icon_batch` / `end_icon_batch`) с привязкой атласа блоков, тем же
шейдером `ui_*.glsl`.

Шрифт: глифы `font_<код Unicode>` --- печатный ASCII, русские буквы и Ё/ё.
Строки обрабатываются как UTF-8 (`src/utils/text/Utf8.h`).

### Локализация

Тексты UI лежат в `assets/lang/<код>.json` (плоский словарь ключ -> строка, `{0}`, `{1}`
--- подстановки). В коде: `tr("menu.singleplayer")`, `tr("worlds.detail", {a, b, c})`
(`src/utils/text/Localization.*`). Английский всегда загружается как запасной, отсутствующий
ключ возвращается как есть. Язык переключается в Options и сохраняется в `options.txt`
(`language=ru`). Новый язык = новый файл в `assets/lang`.

## 36. Игровой цикл

`Game::run()`:

1.  получает `glfwGetTime()`;
2.  вычисляет `delta_time`;
3.  ограничивает delta в `0.001..0.1`;
4.  обновляет FPS counter;
5.  передаёт input/update/render активному Application state.

В gameplay update:

1.  забираются готовые chunk jobs;
2.  забираются готовые mesh jobs;
3.  обновляется day/night;
4.  обновляется Player;
5.  проверяется смерть в Survival;
6.  обновляется Camera;
7.  обновляется положение игрока для Chunk_Manager;
8.  инвалидируются GPU caches выгруженных чанков;
9.  обновляется Block_Interaction; затем, если пришёл запрос на открытие
    контейнера, открывается Container_Session.

Мобы управляются `Mobs_Update` (раздел 47). Периодический тик (фаза Simulate,
приоритет 20) вызывает `Mobs_Update::update_tick`, который обновляет свиней, коров и овец, размножение и
врагов (`update_hostiles`). Лошади обновляются по кадрам в `Mobs_Update::update_frame`. Мобы получают
`Chunk_Manager` для физики. Пока открыт экран контейнера, `update_gameplay`
вызывается с `simulation_active = false` (как при открытом инвентаре).

В gameplay render:

1.  вычисляется sky color;
2.  строятся view/projection;
3.  строится frustum;
4.  получается список renderable chunks;
5.  рисуются sun/moon;
6.  рисуется world geometry;
7.  при необходимости рисуется underwater overlay;
8.  vignette;
9.  block highlight;
10. hotbar;
11. crosshair/health;
12. debug HUD.

## 37. Day/Night

Полный цикл занимает 20 минут реального времени.

Солнце и луна всегда находятся в противоположных направлениях.

Ночь начинается, когда нормализованное время суток >= `Config::night_start_normalized` (0.5, закат).
От этого зависит, нападают ли пауки на игрока (`Mob_Player_View::night`).

Ambient и цвет неба плавно зависят от положения солнца.

Ночная яркость не падает до нуля.

F10, доступный при F3, сдвигает время на одну минуту.

Block light от Sun Stone не уменьшается из-за ночного ambient.

## 39. Оптимизационные принципы

В текущем коде используются несколько независимых уровней оптимизации:

1.  **Плоское voxel storage** --- 32 KiB block grid вместо массивов
    объектов.
2.  **Упакованный light grid** --- 4-bit значения.
3.  **Batch world generation** --- одна климатическая колонка на X/Z.
4.  **Thread-local noise caches** --- отсутствие общей синхронизации
    кэшей между workers.
5.  **Cave cell cache** --- связность на 16³ ячейках.
6.  **Sky cluster cache** --- повторное использование параметров
    островного кластера.
7.  **Layer culling** --- пропуск пустых Y-слоёв.
8.  **Face culling** --- отсутствие невидимых граней.
9.  **Section culling** --- culling 8-блочных Y-секций.
10. **Frustum culling и reachability culling** --- отсечение чанков вне камеры и секций, закрытых от камеры камнем.
11. **GPU occlusion queries** --- отсечение скрытых секций.
12. **Asynchronous generation** --- генерация вне главного потока.
13. **Dedicated mesh worker** --- меши не ждут генерацию.
14. **Mesh snapshots** --- worker не читает живые чанки.
15. **Mesh job deduplication/requeue** --- отсутствие бессмысленного
    накопления одинаковых jobs.
16. **Dirty-only persistence** --- нетронутые чанки не записываются.
17. **Region storage** --- много чанков в одном файле.
18. **RLE persistence** --- однородные чанки хорошо сжимаются.
19. **Separate flora distance** --- дальняя мелкая геометрия может не
    рисоваться.
20. **Deterministic hash rolls** --- дешёвые случайные решения при
    генерации поверхности.

## 40. Важные инварианты проекта

При изменении кода нельзя нарушать следующие условия без
соответствующего изменения всех зависимых подсистем:

### Chunk dimensions

``` text
32 × 32 × 32
```

Это зафиксировано `static_assert` для block/light storage.

### World Y

``` text
-256 .. 1024 inclusive
```

Изменение требует синхронного пересмотра:

-   chunk-Y mapping;
-   streaming;
-   generator;
-   sky islands;
-   persistence validation;
-   player/collision logic.

### Block registry

Runtime ID — `Block_ID` (uint16). Chunk storage хранит палитру из `Block_ID`
и расширяет ширину записи, когда палитра переполняется. Региональный формат пишет
uint16 на воксель (форматы 3–5), старые форматы 0–2 читаются и приводятся к `Block_ID`;
неизвестные id при загрузке заменяются воздухом.

### Mesh boundary

При изменении блока на грани нужно учитывать соседний чанк по
соответствующей оси.

### World generation determinism

Генерация должна оставаться функцией seed + координат + выбранного
генерационного набора, иначе сохранённые нетронутые чанки перестанут
воспроизводиться.

### Main-thread ownership

Живые `Chunk`/`Chunk_Manager` не должны произвольно модифицироваться
worker-потоками.

    ↓

    ↓

## 44. Известные архитектурные ограничения

-   `Chunk_Manager` не является полностью thread-safe.
-   Block light пересчитывается полным BFS в ограниченной области, а не
    инкрементальным снятием света.
-   Mesh rebuild выполняется на уровне всего чанка, хотя внутри mesh
    есть Y-секции.
-   Свет вне загруженных чанков не имеет процедурного fallback и
    считается нулевым.
-   Основной выбор биомов встроен в C++, поэтому редактирование `.biome`
    файлов само по себе не изменяет текущую 23-биомную систему.
-   Persistence region index живёт в памяти до flush.
-   Block_Entity хранятся плоской картой и пишутся в JSON целиком; при
    очень большом числе контейнеров это придётся заменить на поблочное
    хранение по чанкам.
-   При поломке контейнера его содержимое исчезает (выпадающих
    предметов-сущностей в игре нет).
-   Печь --- только слоты и UI, плавки нет (`Block_Entity::progress`
    зарезервирован и не используется).
-   Рецепты: shaped без поворотов/отражений; при крафте из каждой занятой
    ячейки списывается по 1 шт., рецепты с несколькими штуками в одной
    ячейке работают неточно.
-   Мобы: физика --- только гравитация и AABB-коллизии, без прыжков,
    урона от падения и поиска пути.
-   Нетривиальные структуры, выходящие за границы текущего чанка,
    фактически записываются только в тот чанк, который сейчас выполняет
    decoration pass; сама форма детерминирована мировыми координатами,
    но полноценная отдельная очередь межчанковой структуры не
    существует.

## 45. Рекомендуемый порядок изменения подсистем

При изменениях, затрагивающих мир:

``` text
Config
  ↓
World_Generator
  ↓
Chunk / Chunk_Manager
  ↓
World_File / Region_File
  ↓
Renderer / shaders
  ↓
Game / Player / Block_Interaction
```

При изменении block ID или свойств:

``` text
assets/blocks.json
  ↓
Block_Registry
  ↓
World_Generator / Inventory / Mesh builder
  ↓
Renderer shaders/atlas
```

При изменении chunk dimensions обязательно проверять все
`static_assert`, координатные преобразования, region validation,
streaming limits и mesh section calculations.

## 46. Блоки-контейнеры (Block_Entity)

«Блок с начинкой» состоит из двух частей: сам блок в `Chunk_Block_Grid`
(`Chest`/`Crafting_Table`/`Furnace`) и `Block_Entity` с состоянием этого
конкретного блока. `block_entity_type_for(Block_Types)` --- единая точка,
которая говорит, есть ли у типа блока начинка; добавление нового
контейнера начинается с неё.

### Слоты

| Тип            | Слоты | Раскладка                                   |
|----------------|-------|---------------------------------------------|
| Chest          | 27    | 3 ряда по 9                                 |
| Crafting_Table | 9     | сетка 3x3; результат не хранится            |
| Furnace        | 3     | 0 --- вход, 1 --- топливо, 2 --- выход      |

Предмет --- `Item_Stack` из `Inventory.h` (в игре предметы = блоки).

### Жизненный цикл

`Chunk_Manager::sync_block_entity()` вызывается из `set_block_world()`:

-   старый тип --- контейнер, новый другой: Block_Entity удаляется, связь
    двойного сундука разрывается;
-   новый тип --- контейнер: создаётся пустой Block_Entity;
-   тот же тип контейнера: содержимое не трогается.

### Двойной сундук

При постановке сундука проверяются 4 горизонтальных соседа на той же
высоте. Если сосед --- одиночный сундук, оба получают `paired_dx/dz`
(смещения друг к другу). Тройные цепочки невозможны. На экране открытого
сундука вторая половина идёт сразу за первой (54 слота).
`Chunk_Manager::get_paired_block_entity()` возвращает партнёра или
`nullptr` при рассинхроне.

### Экран и клики (`Container_Session`)

Раскладка логических индексов `click_slot`: слоты контейнера, слоты
второй половины (если есть), затем хотбар игрока. Слот результата верстака
--- отдельный маркер `k_output_slot`. Поведение:

-   клик по слоту контейнера: слияние стаков одного типа (до 64) или swap
    с курсором;
-   хотбар в Survival: делегируется `Inventory::click_panel_slot` через
    `set_carried_stack`;
-   хотбар в Creative: пустая рука берёт 1 шт. блока слота, занятая рука
    очищается;
-   выход печи: только забирать;
-   результат верстака: `Recipe_Registry::match` по сетке; клик забирает
    результат и списывает по 1 шт. из каждой занятой ячейки;
-   закрытие: стак на курсоре в Survival возвращается в инвентарь.

### Рецепты

`assets/recipe.json`, загружается один раз `Recipe_Registry`:

``` json
{"recipes":[
  {"name":"oak_planks_from_log","type":"shapeless",
   "ingredients":[{"item":"Oak Log","count":1}],
   "output":{"item":"Oak Planks","count":4}},
  {"name":"crafting_table","type":"shaped",
   "pattern":["PP","PP"],"key":{"P":"Oak Planks"},
   "output":{"item":"Crafting Table","count":1}}
]}
```

`item` --- имя блока из `blocks.json`. Shaped: узор до 3x3, символ пробел =
пустая ячейка, сравнение по ограничивающему прямоугольнику непустых ячеек
без поворотов. Shapeless: сравнение суммарных количеств по типам.
Рецепты с неизвестным предметом пропускаются с записью в лог.

## 47. Мобы

Все мобы управляются `Mobs_Update` (`src/mobs/Mobs_Update.*`): он хранит списки свиней,
коров, овец, лошадей и врагов, спавнит их и вызывает их обновление. Игра передаёт ему
`Mob_Player_View` (позиция, скорость, `sneaking`, `alive`, `night`) и `Chunk_Manager`.

Тики:

-   `update_tick` (фаза Simulate): спавн и обновление свиней, коров, овец; размножение; враги
    (`update_hostiles`);
-   `update_frame` (по кадрам): лошади и езда.

Виды:

-   пассивные: `Pig` (`Pig_AI`), `Passive_Animal` (корова, овца);
-   лошадь: `Horse` (`Horse_AI`), приручение, езда, дикая лошадь пугается игрока;
-   враги: `Hostile_Mob` с видом `Hostile_Kind` (`Zombie`, `Skeleton`, `Spider`). Параметры — в
    `hostile_stats()` (`src/entities/hostile/Hostile_Mob.cpp`) и в `Config.h` (`*_attack_damage`,
    `*_run_speed`, `*_detect_range`, `min_*_count`, `*_spawn_radius_*`).

Враги:

-   спавнятся только в Survival (`Mobs_Update::set_hostiles_enabled`, ставится `Game` при
    создании мира и переключении режима);
-   видят игрока дистанцией `detect_range` (вдвое меньше, если он крадётся) и лучом через блоки;
    тревога поднимает врагов рядом;
-   пауки видят игрока только ночью (`Mob_Player_View::night`);
-   `Hostile_Mob::update` возвращает `Hostile_Result` с двумя полями: `player_damage` (урон игроку до
    брони) и `horse_damage` (удар по лошади, если `hit_horse`);
-   урон по игроку растёт от его скорости сверх ходьбы: `attack_damage * (1 + over_walk *
    mob_speed_bonus_per_speed)`, без потолка;
-   паук в `Hostile_Context.prey_valid` (ближайшая живая лошадь в `spider_detect_range`) гонится за
    лошадью, а не за игроком, и бьёт её, когда она в досягаемости.

Лошадь и паук:

-   лошадь без всадника, не в панике (`Flee`/`Scared`), бежит к ближайшему пауку в
    `Config::horse_hunt_range` (`Horse_Context.prey_valid`);
-   удар делает `Horse::attack` (кулдаун `horse_attack_cooldown`); результат забирает
    `Mobs_Update::update_frame` через `Horse::consume_attack()` и наносит урон пауку;
-   удар паука по лошади наносит `Mobs_Update::update_hostiles` через `Horse::take_damage`.

Бой игрока (`Mobs_Update::interact`):

-   перезарядка удара — `attack_cooldown` инструмента в руке (кулак — `Config::player_attack_cooldown`);
-   урон — `attack_damage` инструмента (кулак — `Config::player_fist_damage`), умноженный на
    `1 + over_walk * melee_speed_bonus_per_speed * speed_damage_scale`, где `over_walk` — скорость
    игрока сверх `player_move_speed`; потолка нет;
-   `speed_damage_scale` и `attack_cooldown` задаются в `assets/blocks.json` у каждого инструмента.

Оружие (`"tool": "weapon"` в blocks.json, id 106–123):

-   поля предмета: `attack_damage`, `attack_cooldown`, `speed_damage_scale`, `durability`; у копья и
    трезубца ещё `impulse_speed` (на суше), `impulse_speed_water` (в жидкости, если не задан — как
    `impulse_speed`) и `impulse_cooldown` (если не задан — `Config::tool_impulse_cooldown`);
-   импульс срабатывает по ПКМ только в Survival и тратит 1 прочность (`Game::handle_tool_impulse`);
-   после удара моб неуязвим 0,4–0,5 с (`*_invulnerable_seconds` в `Config.h`): перезарядка оружия
    меньше этого времени даёт пропущенные удары, при этом прочность всё равно тратится.

Физика (общая для наземных мобов):

-   вертикальная скорость копится каждый кадр:
    `v = max(mob_max_fall_speed, v + mob_gravity * dt)`;
-   гравитация общая: `Config::mob_gravity = -20.0`, `Config::mob_max_fall_speed = -40.0`;
-   оси X, Z и Y проверяются раздельно AABB-тестом против solid-блоков, поэтому моб
    останавливается на полу и не проходит сквозь стены;
-   `update(dt, const Chunk_Manager&)` получает мир параметром, а не хранит ссылку.

Модели: `assets/mobs/*.glb`. Врагу нужны клипы `Idle` и `Walk`, `Attack` необязательный. Если модель не
загрузилась, спавн пишет ошибку и откладывает попытку (для врагов — 30 с).

## 48. Режимы игры, полёт и инвентарь

- Режимы: `Game_Mode {Creative, Survival}` и флаг `Game::m_spectator` (наблюдатель — это Creative с полётом сквозь блоки).
- F1 вызывает `Game::cycle_game_mode()`: Survival → Creative (полёт с коллизиями) → наблюдатель (`noclip`) → Survival.
- `Game::apply_game_mode(mode, spectator)` — единая точка смены режима: выставляет инвентарь, мобов,
  урон/голод, полёт (`Player::set_flying`) и `noclip` (`Player::set_noclip`).
- Полёт с коллизиями — `Player::move_flying_with_collision`: движение по осям по очереди, упёрся — скорость
  и импульс по этой оси обнуляются. `noclip` — прежнее свободное движение.
- Инвентарь один для обоих режимов: хотбар и хранилище (`Inventory::m_hotbar`, `m_storage`) хранят реальные
  стаки. Палитра Creative (`get_palette_slot`) — бесконечный источник: клик берёт копию на курсор
  (`m_carried_infinite`), которая кладётся в обычные слоты через `place_infinite`. Курсор из палитры при
  закрытии панели отпускается, реальный стак возвращается в инвентарь.
- Слоты панели: 0..26 хранилище, 27..35 хотбар, палитра — id 400..426 (`Panel_Slot_Ids::k_creative_palette_base`).
- Сундук/верстак/печь показывают хранилище игрока в обоих режимах (`Container_Session` без творческой ветки).

## 49. Палитра блоков и ширина ID

- `Chunk_Block_Grid`: палитра `std::vector<Block_ID>`, индексы упакованы в 0/1/2/4/8/16 бит.
  Переполнение палитры вызывает `repack` на следующую ширину (см. `bits_for_palette`).
- Мешер: CPU-ключ слияния — 64 бита: id 0..15, meta 16..23, свет 24..31, AO 32..39
  (`Chunk.cpp`, константы `kKeyPresent`, `kKeyRotate` — 40/41 бит). Шейдер `mesh_greedy.comp` — `uvec2`
  с той же раскладкой (.x = id | meta<<16, .y = свет | AO<<8).
- GPU-каналы (`pack_channel`) — шаблон по ширине значения; палитра канала хранится в 32-битных словах.
- Таблица правил для GPU: `[light_coarse 256 слов][block_flags по id]` — порядок зафиксирован в шейдере.
- Региональный файл: форматы 0–2 (байт на воксель) читаются, пишутся 3 (raw16), 4 (RLE16), 5 (метаданные + RLE/raw16).
- Проверка без GPU: headless-тест палитры на 1000 id и кругового прохода региона (см. историю версии 8.7).

## 50. Время суток по измерениям и привязка чанка

- `Dimension_Info::time_mode`: `Cycle` (свои часы) или `Fixed` (отметка `fixed_time`, часы заморожены).
- `Game::load`: для `Fixed` вызывает `set_frozen(true)` и ставит `fixed_time`; для `Cycle` — `day_time` из `world.json`.
- `Game::save_world`: замороженное время не пишется в `world.json`.
- `Chunk::m_dimension` задаётся `World_Generator::get_dimension_id()` в конструкторе; хранение по `storage_key`.
- Ограничение: одно измерение в памяти; для нескольких одновременно (фаза 7) время нужно хранить по измерениям.

## 51. Типы мира

Тип мира — это измерение из `Dimension.cpp` плюс (для «один биом») биом в `World_Settings::biome`.
Экран «Создание мира» (`State_Create_World`, `Application.cpp`) перебирает пять типов через кнопку
«Тип мира» и показывает кнопку «Биом» только для измерений с `single_biome`.

- `Dimension_Info`: новые флаги `caves` (пещеры), `ground` (есть ли земля под островами) и `single_biome`
  (весь мир одного биома). Флаг `sky_islands` теперь читается генератором; раньше острова
  генерировались всегда, а флаг был декоративным.
- `superflat` — `Terrain_Mode::Flat` со слоями: глубинный камень до Y=-1, камень 0..2, земля 3..4, трава 5.
- `single_biome` — `Terrain_Mode::Noise`, `caves = false`, `sky_islands = false`, `single_biome = true`.
- `single_islands` — то же, но `ground = false`, `sky_islands = true`, без декораций.
- `World_Generator::set_biome(Biome_Id)`: в измерении с `single_biome` `surface_biome_for_column` и
  `biome_at` возвращают выбранный биом; климатические поля и рельеф остаются обычными.
- `ground = false`: `block_in_column` возвращает воздух; чанки ниже Y=200 пусты
  (`generate_chunk` выходит раньше, `chunk_is_definitely_air` возвращает true).
- Острова в `ground = false` ставятся с `anchor_valid = true`, центр — Y 290..350. Низ самого большого
  острова — центр − 66, поэтому он не обрезается по Y=200. В обычном мире якорь и центр не меняются.
- `World_Generator::find_spawn_surface(x, z)`: для мира с землёй возвращает `get_height`; без земли ищет
  ближайший остров кольцами до радиуса 256 с шагом 8 и меняет x, z. Если островов нет — Y=220 (игрок упадёт;
  нужен `/tp`).
- `World_File`: поле `biome` в `world.json` (по умолчанию `Plains`), читается и пишется как остальные поля.
- `Game::create_world(..., dimension, biome, error)`: записывает оба поля; `setup_world_objects` и
  `reload_world` вызывают `set_biome(biome_from_name(...))` и `find_spawn_surface`.
- Проверка (headless): супер плоский — земля на Y=5; один биом — 0 пещер из 8712 выборок (в обычном мире 205),
  биом совпадает во всех выборках; острова — 0 блоков ниже Y=200, острова есть в ~25% колонок.
- Не проверено в игре: отрисовка островов и их граница по Y=200 в рендере, поведение на старых сохранениях.

## 52. Перенос id камня и удаление «Oak Wood»

- `Block_Types::Stone` = 5 (раньше 3). `Block_Types::Oak_Wood` удалён; дубовый ствол — `Block_Types::Oak_Log` = 56
  (запись из `blocks.json`).
- id 3 не зарегистрирован: `Block_Registry::is_known(3) == false`. Старые данные с id 3 при чтении региона
  приводятся к воздуху (как и любой неизвестный id).
- id 8 зарезервирован под динамит (`reserved_block_ids` в `blocks.json`) и не используется.
- Из данных убраны все ссылки на «Oak Wood»: тег `logs` и рецепт досок в `recipe.json`, входы и топливо в
  `smelting.json`. Деревья (`Tree_Generator`) ставят `Oak_Log`.
- Проверено headless: реестр даёт `3 → нет`, `5 → Stone`, `8 → зарезервирован`, `56 → Oak Log`.

## 53. Запись сгенерированных чанков и приоритет очереди

- `Chunk_Manager::worker_loop`: сгенерированный чанк сразу пишется через `World_File::save_chunk`, до передачи
  главному потоку (чанк ещё принадлежит воркеру). Загрузка с диска по-прежнему идёт первой.
- `unload_chunk` / `save_chunk_to_disk` без изменений: нетронутый чанк при выгрузке не перезаписывается, изменённый — пишется.
- `reprioritize_pending_jobs()` вызывается из `update_player_position` при смене чанка игрока: перестраивает
  `m_pending_jobs` по `chunk_job_priority` (квадрат горизонтального расстояния + 4 × dy²), задачи вне
  `is_chunk_wanted` снимаются и чистят `m_requested_chunks`.
- Воркер снимает снимок `generator`, `World_File` и `generation_folder` вместе с задачей, под `m_job_mutex`;
  задача с `generation_id` от прошлого мира пропускается.
- Проверено headless (`Chunk_Manager` + регионы, быстрое перемещение 16 блоков за кадр): все загруженные рядом с
  игроком чанки (75/75) и все пройденные (28/28) читаются с диска.
- Не проверено: задержка записи на реальном диске при 50 блоках/с и поведение на огромной очереди в игре.

## 54. Булыжник

- `Block_Types::Cobblestone` = 3 (бывший свободный id). `Stone` (5) в `blocks.json` имеет `"drop": "Cobblestone"`:
  `Dropped_Item` читает `drop_id` при добыче, и камень выпадает как булыжник.
- Переплавка: `smelting.json` — `Cobblestone` → `Stone`, 1 шт., 10 с.
- Спрайт `cobblestone` — ячейка (96, 16) в `texture_atlas.png`, запись в `blocks_main.atlas.json`. Нарисован процедурно.
- Проверено headless: id 3 — Cobblestone, `drop_id` камня = 3.
