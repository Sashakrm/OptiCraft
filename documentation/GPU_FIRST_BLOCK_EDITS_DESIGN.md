# GPU-first обновление блоков: предлагаемая архитектура

## Текущее состояние

Сейчас CPU остаётся авторитетным владельцем voxel state чанка. При правке блока `Chunk_Manager` меняет CPU-данные, помечает меш/свет грязными и ставит срочную задачу. CPU собирает packed snapshot чанка и отправляет его на GPU; compute-шейдеры строят геометрию, а Renderer публикует indirect-команды.

**Асинхронная замена GPU-меша уже реализована:** новый mesh строится в отдельном pending/COW handle, прежний active handle продолжает отрисовываться. После fence Renderer проверяет готовность через `glClientWaitSync(..., 0)` без ожидания; обратно читаются только quad counters/status, не сами mesh bytes. При успешной проверке CPU переключает active handle и метаданные на новую генерацию. В обычном игровом режиме этот путь не блокирует кадр.

Это всё ещё не полное GPU-first редактирование voxel state: packed snapshot готовится на CPU, а GPU получает уже изменённое состояние блока и строит из него новую геометрию. GPU пока не является владельцем самого массива блоков.

## Почему нельзя просто прочитать блок обратно с GPU после каждого клика

Если после каждого изменения сделать синхронный `glGetBufferSubData`/map, CPU будет ждать завершения GPU-команд. Это создаёт pipeline stall и может быть медленнее нынешней асинхронной схемы. Кроме того, физика игрока, raycast, AI, распространение света, жидкости, сохранения и генерация соседних граней сейчас читают CPU voxel state. Перенос только мешинга на GPU не делает эти подсистемы автоматически согласованными.

## Предлагаемый pipeline

1. **Persistent voxel SSBO на GPU.** Для каждого resident chunk handle хранить 32³ block IDs и metadata в устойчивом GPU-буфере. Сопоставление `handle -> voxel range` должно иметь generation/version, чтобы запоздавшая команда старого чанка не меняла повторно использованный handle.
2. **Sparse edit queue.** CPU при действии игрока отправляет короткую запись `{handle, local_xyz, block_id, meta, edit_sequence}` в кольцевой SSBO. Это не полный snapshot чанка. Очередь ограничена по размеру; переполнение переводит только этот чанк на безопасную полную синхронизацию.
3. **Compute apply.** Compute shader применяет edit records к persistent voxel SSBO, отмечает dirty section bits и соседние секции, если изменение касается границы 8-блочной секции. Отдельно учитываются соседние чанки для граней/AO.
4. **Section remesh в back-buffer.** Compute mesher читает persistent voxel SSBO и строит только изменённые секции в новый диапазон quad pool. Старые диапазоны остаются отображаемыми, пока новый меш не завершён. Это исключает кадр с пустым/частичным мешем.
5. **GPU commit.** После `glMemoryBarrier` и проверки overflow GPU-side draw metadata получает новую версию/диапазоны. Renderer использует новые команды только когда вся изменённая секция готова. При переполнении выполняется повторная сборка с увеличенным диапазоном; старый меш продолжает отображаться.
6. **CPU simulation mirror.** CPU немедленно обновляет свой block state для физики, raycast, жидкостей, света и AI; этот шаг не ждёт GPU. Таким образом визуальная ветка может стартовать через sparse GPU edit, а игровой мир остаётся согласованным.
7. **Асинхронное сохранение.** CPU уже знает изменённый block ID, поэтому может записать delta-save без readback GPU. Периодический readback GPU нужен только для проверки/восстановления или если в будущем часть состояния будет меняться исключительно на GPU; он идёт через staging ring + fence и никогда не блокирует текущий кадр.

## Правила синхронизации и fallback

- Все edit records упорядочены `edit_sequence`; повторно использованные handles проверяются по generation.
- Между apply-edits, remesh, bounds build и indirect draw выставляются соответствующие shader-storage, vertex-attrib и command barriers.
- Старый mesh остаётся активным до атомарного commit нового section version.
- При unload чанка его queued edits либо завершаются, либо отменяются по generation; они не могут попасть в новый чанк на той же позиции.
- При изменении типа блока, затрагивающем свет/жидкость/физику, GPU не подменяет CPU simulation: CPU получает то же действие в том же порядке.
- При ошибке шейдера, переполнении edit queue или потерянной GPU-резидентности чанк переключается на текущую snapshot-пересборку. Состояние мира не теряется.

## Почему persistent GPU voxel state не включён в 0.10.8.5

В текущем коде нет persistent GPU voxel buffer и безопасного handle-generation протокола для такого буфера. Добавить только edit SSBO без double-buffered section geometry, overflow handling и согласования с CPU simulation означало бы получить редкие потерянные блоки или кадры с частично очищенным мешем. Поэтому 0.10.8.5 сохраняет безопасную асинхронную COW-замену готового GPU-меша, но не объявляет persistent GPU voxel state реализованным. Полный sparse-edit pipeline остаётся следующим крупным этапом, а не выдается за уже работающую функцию.
