# Профилирование (Tracy)

Документ описывает, как снимать профиль OptiCraft профайлером Tracy, какие участки размечены, и что показали первые измерения. Статический разбор узких мест — в [`problems.md`](problems.md); здесь — замеры.

## 1. Подключение

Tracy лежит в `external/tracy` (версия **v0.14.1**) и **не хранится в git**: папка перечислена в `.gitignore`. Клонировать заново:

```bash
git clone --depth 1 --branch v0.14.1 https://github.com/wolfpld/tracy.git external/tracy
rm -rf external/tracy/.git
```

Сборка:

```bash
cmake -S . -B cmake-build-profile -DCMAKE_BUILD_TYPE=Release
cmake --build cmake-build-profile -j
```

- Если `external/tracy` есть, клиент собирается автоматически (`TRACY_ENABLE`). Отключить: `-DOPTICRAFT_TRACY=OFF`.
- Если папки нет, проект собирается как раньше: макросы из `src/utils/profiling/Profiler.h` становятся пустыми.
- GUI-профайлер `tracy-profiler` — отдельная цель (`OPTICRAFT_TRACY_PROFILER`, по умолчанию ON). В обычную сборку `all` она не входит и собирается только по запросу.
- Для **чистых** замеров производительности (без накладных расходов Tracy) собирайте с `-DOPTICRAFT_TRACY=OFF`.

Макросы (`src/utils/profiling/Profiler.h`):

| Макрос | Назначение |
|---|---|
| `OC_ZONE("имя")` | замер от этой строки до конца блока `{}` |
| `OC_FRAME_MARK` | конец кадра (счётчик FPS в Tracy) |
| `OC_PLOT("имя", значение)` | числовой график (в проекте пока не используется) |

## 2. Что размечено

- **Кадр**: `Frame` (Game::run), `swap_buffers` (здесь — «Frame tail: GPU present»), `poll_events`.
- **Состояния приложения**: `App::handle_input`, `App::update`, `App::render`, `Input_Manager::update`.
- **Геймплей**: `Game::update_gameplay`, `Game::render_gameplay`, `Mobs::update_frame`, `Logic::update`, `Fluid::update`.
- **Чанки (главный поток)**: `ChunkMgr::update_player_position`, `collect_finished_chunks` (с подзонами вставки и скана света), `flush_urgent_mesh_rebuilds`, `enqueue_mesh_rebuild`, `rebuild_dirty_chunks`, `recompute_sky_lighting`, `relight_*`, `load_around`, `unload_distant`, `get_renderable_chunks`, `reprioritize_*`, `update_fluids`.
- **Генерация (рабочие потоки)**: `Gen::generate_chunk_column`, `Gen::generate_chunks`, `Gen::generate_prepared_chunk_impl`.
- **Рендер**: `Renderer::render_chunks`, `prepare_gpu_frame`, `submit_gpu_batch` (с подзонами: подготовка заголовков, загрузка SSBO, диспетчеризация мешера, копия readback), `draw_gpu_kind`, `build_gpu_hiz`, `poll_gpu_readbacks`, `grow_gpu_pool`, `draw_sky`.

Замер на очень частой функции (`decorate_column`, 8 млн вызовов за прогон) был убран: его собственные накладные расходы сопоставимы с измеряемым временем.

## 3. Как снять профиль

**В CLion — одна конфигурация запускает и игру, и профайлер.**

1. Один раз установить системные зависимости профайлера (Debian/Ubuntu):
   ```bash
   sudo apt install libglfw3-dev libcapstone-dev libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev libgl-dev
   ```
2. Открыть проект в CLion. При первой конфигурации CMake скачает зависимости профайлера (zstd, ImGui и др.), поэтому нужен интернет. Цель `tracy-profiler` появится в списке run-конфигураций.
3. В выпадающем списке выбрать **OptiCraft + Tracy** и нажать Run (Shift+F10). Сначала стартует окно `tracy-profiler`, затем игра.
4. Игра подключается к профайлеру сама (порт 8086). Если в окне профайлера записи не появилось, нажмите **Connect** (адрес `127.0.0.1`). Клиент Tracy переподключается, поэтому порядок запуска не важен: проверено, что игра, стартовавшая раньше профайлера, попадает в запись.
5. Запись сохраняется через меню самого профайлера.

Конфигурация лежит в `.idea/runConfigurations/OptiCraft_with_Tracy.xml`. Если CLion её не показал, создайте вручную: Run → Edit Configurations → **+** → Compound, и добавьте две конфигурации: `tracy-profiler` и `OptiCraft`.

Обычная конфигурация `OptiCraft` запускает игру без окна профайлера.

Для **настоящих** замеров используйте Release: в Settings → Build, Execution, Deployment → CMake добавьте профиль Release и запускайте из него. Debug собирается без оптимизаций, и цифры будут сильно отличаться.

Профайлер можно собрать и отдельно: `cmake --build cmake-build-debug --target tracy-profiler`, бинарник появится в `cmake-build-debug/tracy-profiler/tracy-profiler`.

**Без GUI (для тестов).** Соберите `tracy-capture` и `tracy-csvexport` из `external/tracy/capture` и `external/tracy/csvexport`, затем:

```bash
TRACY_CAPTURE=/путь/к/tracy-capture tools/profiling/run_scenario.sh travel cmake-build-profile creative tools/profiling/travel.tl
```

Скрипт поднимает Xvfb (если `DISPLAY` не задан), запускает игру с `OPTICRAFT_AUTOSTART` и подаёт команды из таймлайна через `OPTICRAFT_CMDFILE`. Результат — `profiling-results/<имя>/<имя>.tracy`.

Таймлайны:

- `tools/profiling/idle.tl` — стоять на месте (выживание), 90 с.
- `tools/profiling/travel.tl` — полёт в креативе, шесть перелётов на 300–500 блоков (стриминг и генерация).
- `tools/profiling/edit.tl` — 144 установки и удаления факела рядом с игроком (освещение).

Сводка по зонам из записи:

```bash
tracy-csvexport file.tracy        # суммарное время, число вызовов, среднее, максимум
tracy-csvexport -e file.tracy     # собственное время (без вложенных зон)
tracy-csvexport -u file.tracy     # каждый вызов отдельно (для поиска выбросов; файл большой)
```

## 4. Условия замеров

- Контейнер: 2 vCPU, Mesa 25.2 (llvmpipe, **программный OpenGL 4.5**), Xvfb, vsync выключен.
- Сборка: Release (`-O3 -march=native`), LTO выключен (для скорости итераций; по умолчанию в проекте LTO включён).
- Мир: seed 123, стандартный генератор.
- Накладные расходы Tracy не измерялись отдельно. Сценарии запускались по нескольку раз (`idle`: 65–68 мс за средний кадр, `travel`: 78, 81 и 82 мс), разброс порядка 5%.

**Главная оговорка.** На этой машине вся графика идёт **на процессоре**: растеризация, сброс буфера и компьют-мешер чанков выполняются llvmpipe на тех же двух ядрах, что и игра. Поэтому доли рендера ниже **не отражают** реальную видеокарту и не годятся для выводов о рендеринге в целом. Выводы о главном потоке (логика чанков, света, жидкостей) от этого почти не зависят.

## 5. Результаты

### 5.1 Сценарии

| Сценарий | Кадров | Средний кадр | Макс. кадр | FPS (≈) |
|---|---:|---:|---:|---:|
| `idle` — стоять, выживание | 1416 | 67.3 мс | 166 мс | 15 |
| `travel` — перелёты, креатив | 836 | 81.0 мс | 224 мс | 12 |
| `edit` — правки блоков | 1021 | 80.5 мс | 177 мс | 12 |

### 5.2 Где уходит время кадра (доля от суммы кадров)

| Зона | idle | travel | edit |
|---|---:|---:|---:|
| `App::render` (весь рендер) | 65.8% | 73.1% | 70.0% |
| — компьют-мешер чанков (`GPU mesher dispatch`) | 12.2% | 42.9% | 17.9% |
| — растеризация (`draw_gpu_kind`) | 44.5% | 23.2% | 43.8% |
| — сброс буфера (`GPU present`) | 32.1% | 18.2% | 27.2% |
| — Hi-Z пирамида (`build_gpu_hiz`) | 4.1% | 0.1% | 3.6% |
| `App::update` (логика) | 1.9% | 8.6% | 2.3% |
| — `update_player_position` (смена чанка) | 1.6% | 7.0% | 1.9% |

Процессы, которые идут в фоне: генерация мира в рабочих потоках — `generate_prepared_chunk_impl` в среднем **≈4 мс на чанк** (travel: 4150 чанков, 16.7 с суммарного времени потоков).

### 5.3 Логика на главном потоке (то, что останется и на реальной видеокарте)

Доли от суммы кадров в сценарии `travel`:

| Зона | Доля | Вызовов | Среднее | Замечание |
|---|---:|---:|---:|---|
| `enqueue_mesh_rebuild` | **3.9%** | 13 314 | 197 мкс | копирование сетки чанка на главном потоке |
| `collect_finished_chunks` | 3.6% | 845 | 2.9 мс | вставка готовых чанков; скан света — 0.6% |
| `flush_urgent_mesh_rebuilds` | 2.0% | 845 | 1.6 мс | срочные перестроения мешей |
| `recompute_sky_lighting` | 1.9% | 1 461 | 0.87 мс | пересчёт неба по колонкам |
| `Fluid::update` | 1.0% | 1 189 | 0.57 мс | жидкости |
| `rebuild_dirty_chunks` | 0.6% | 845 | 0.49 мс | |
| `get_renderable_chunks` | 0.6% | 760 | 0.54 мс | |
| `collect_finished_mesh_jobs` | 0.4% | 845 | 0.28 мс | |

В `edit` освещение стоит дёшево: `relight_block_light_near` — 0.28 мс на правку, `relight_sky_light_near` — 1.2 мс (всего 144 правки). Перестроение мешей после правки (`enqueue_mesh_rebuild`) здесь тоже заметно: 1.3% кадра.

### 5.4 Пики кадров

В `travel` **268 из 836 кадров (32%) длиннее 100 мс**; они занимают 34 с из 68 с. В 263 из этих кадров доминирует `App::render`, в 245 — `prepare_gpu_frame` (компьют-мешер). То есть самые тяжёлые кадры — это моменты, когда приходит пачка новых чанков и их меши ставятся на перестроение. Логика игры в пиках почти не участвует.

Отдельные одиночные выбросы на главном потоке (177 мс и 84 мс внутри скана света в одном из прогонов) при среднем 84 мкс на вызов скорее всего вызваны остановками потока из-за конкуренции за два ядра. Это предположение, не проверенное независимым таймером.

## 6. Выводы

1. **На этой машине главный тормоз — программная графика.** Компьют-мешер чанков, растеризация, сброс буфера и Hi-Z вместе занимают **84–93% кадра** (llvmpipe). Реальные узкие места рендера можно увидеть только на машине с видеокартой.
2. **Из логики главного потока самое дорогое — смена чанков.** `update_player_position` занимает 7% кадра при перелётах; основная часть — `enqueue_mesh_rebuild` (3.9% кадра, вызывается из нескольких мест) и вставка готовых чанков. Это совпадает с описанием в `problems.md` (п. 3.2), но теперь подтверждено замером.
3. **Освещение при правке блока дешёвое**: пересчёт блочного света ≈0.3 мс, неба ≈1.2 мс на правку (главный поток). Это согласуется с замерами в `problems.md` (≈19 → ≈3 мс для правки с лавой).
4. **Жидкости и пересчёт неба** на главном потоке стоят около 3% кадра при перелётах, без пиков.
5. **Генерация мира** стоит около 4 мс на чанк в рабочих потоках. Главному потоку она не мешает, пока рабочие не голодают; внутри функции пока не разбита (см. далее).

## 7. Что дальше (не сделано)

- Повторить `travel` и `edit` на машине с видеокартой. Для настоящих GPU-замеров добавить `TracyGpuZone`/`TracyGpuContext` вокруг диспетчеризации мешера и проходов отрисовки.
- Разбить `generate_prepared_chunk_impl` на стадии (рельеф, пещеры, реки, декорации, деревья).
- Кандидаты для оптимизации главного потока по убыванию доли: `enqueue_mesh_rebuild` (копирование сетки и соседей), `recompute_sky_lighting`, `Fluid::update`.
- Для GPU-пути: `glBufferData(..., nullptr)` с orphaning на каждый батч в `submit_gpu_batch` и `glMemoryBarrier` внутри батча — кандидаты, которые стоит проверить на настоящей видеокарте.

## 8. Заметки

- Зоны `swap_buffers` и `poll_events` при первом прогоне не попадали в выгрузку `tracy-csvexport` (причина не выяснена); они переименованы в `Frame tail: …`, и после этого записываются.
- Результаты прогонов лежат в `profiling-results/` (игнорируется git). Файлы `.tracy` также игнорируются.

## 9. Посекундный отчёт сессии для ИИ (DeepSeek и др.)

Tracy сам посекундные итоги не пишет: он сохраняет полную запись `.tracy`. Посекундная таблица строится
из этой записи скриптом `tools/profiling/summarize_trace.py`. Обёртка `tools/profiling/capture_session.sh`
делает всё за один запуск.

### 9.1 Запуск в CLion

Запустите конфигурацию **OptiCraft session + report** (файл `.idea/runConfigurations/OptiCraft_session_report.xml`).
Игра стартует в креативе, запись идёт сама. Чтобы закончить сессию, закройте окно игры (или нажмите Stop в CLion).
Результаты появятся в `profiling-results/session-ДАТА-ВРЕМЯ/`.

Если конфигурация не появилась в CLion, создайте её вручную: **Run → Edit Configurations → + → Shell Script**,
Script path: `tools/profiling/capture_session.sh`, Working directory: корень проекта, Execute in terminal: включено.

Из терминала (нужен запущенный X-сервер, например `Xvfb :99 &` и `export DISPLAY=:99`):

```bash
SESSION_SECONDS=60 tools/profiling/capture_session.sh cmake-build-debug/OptiCraft   # ровно 60 секунд
SESSION_MODE=survival tools/profiling/capture_session.sh                           # выживание вместо креатива
```

При первом запуске скрипт сам собирает `tracy-capture` и `tracy-csvexport` в `cmake-build-debug/tracy-tools`
(нужны `libzstd-dev` и `libcapstone-dev`). Сборка идёт отдельным проектом, поэтому цели Tracy не конфликтуют с клиентом.

### 9.2 Что получится

В папке сессии:

- `session.tracy` — полная запись (открывается в Tracy Profiler);
- `session_per_second.csv` — таблица, одна строка на секунду;
- `session_summary.md` — то же в Markdown, плюс сводка по кадрам и список 20 самых долгих кадров (> 100 мс) с главной причиной;
- `game.log`, `capture.log` — журналы для диагностики.

Файл `session_per_second.csv` или `session_summary.md` можно целиком вставить в ИИ-чат и попросить анализ.

### 9.3 Как читать колонки

- Все колонки `*_ms` — суммарное время зон, **начавшихся в эту секунду**. Это сумма, а не среднее: `present_ms = 681` при `frames = 72`
  значит, что 72 вызова swap заняли по ~9,5 мс каждый.
- Колонки главного потока (render, update, input, present, mesher, draw, hiz, player_pos, enqueue_mesh, collect_chunks,
  light_scan, sky_light, fluid, mobs) не перекрываются, их сумма обычно ≤ 1000 мс.
- Колонки `gen_*` — рабочие потоки генерации, суммируются по всем потокам и могут превышать 1000 мс.
- `chunks_applied`, `gen_chunks` — количество событий в секунду, не время.

### 9.4 Проверка

Суммы по секундам совпадают с сырым экспортом `tracy-csvexport -u session.tracy` (проверено на тестовой 25-секундной сессии:
`present_ms` в первой секунде 681,3 мс в обоих источниках).
